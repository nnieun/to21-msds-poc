# 성능 측정 결과 (2026-11-08)

조건: Lambda 1x H100 PCIe 80GB, vLLM 0.32.0, Qwen3.6-35B-A3B-FP8, `max_model_len 49152`, `max_num_seqs 8`, `gpu_memory_utilization 0.92`, prefix caching 켬. 앱은 `MSDS_PREPROCESS=legacy`(OCR·Docling 없는 전처리). 계획은 [PERF_PLAN.md](PERF_PLAN.md), 원본 데이터는 `perf-results/`.

> **이 결과는 OCR(글자추출)·Docling이 없는 구성의 기준선입니다.** 프로젝트의 최종 전처리(version17, PaddleOCR + Docling, GPU)는 아직 측정 전이고, 이 문서의 숫자를 "전체 파이프라인 성능"이라고 쓰면 안 됩니다. OCR 포함 측정은 같은 PDF 6건으로 따로 하고 이 기준선과 비교합니다.

## 2. vLLM 단독: 동시 요청 수에 따른 변화 (E1, 합성 부하)

`vllm bench serve`, 무작위 토큰 입력 3,800 / 출력 700 고정, 요청 수는 동시성의 8배(최소 32), 각 1회. 이 부하는 내용이 무작위라 **prefix 캐시가 먹히지 않는다**(실제보다 첫 토큰이 나쁘게 나옴).

| 동시 | 처리량 (tok/s) | 1개 대비 | 첫 토큰 p50 / p95 (ms) | 토큰 간격 p50 (ms) | 응답 시간 p50 / p95 (ms) |
|---|---|---|---|---|---|
| 1 | 170.2 | 1.0배 | 318 / 343 | 5.4 | 4,063 / 4,278 |
| 2 | 287.7 | 1.7배 | 346 / 359 | 6.5 | 4,862 / 4,944 |
| 4 | 440.8 | 2.6배 | 382 / 397 | 8.6 | 6,364 / 6,446 |
| 8 | **625.0** | **3.7배** | 617 / 1,642 | 11.4 | 9,067 / 9,683 |
| 16 | 620.6 | 3.6배 | **8,804 / 11,041** | 11.8 | 17,402 / 19,557 |

vLLM 내부 상태(같은 시간대): 동시 8에서 대기 요청 평균 0.1(최대 4), **동시 16에서 대기 평균 6.6(최대 8)**, KV 캐시 사용률은 최대 4.4%.

해석:
- **처리량은 동시 8에서 포화**한다(625 → 621). `max_num_seqs=8`이 한계선이다.
- 8을 넘기면 처리량은 그대로이고 **초과분이 vLLM 안에서 대기**해 첫 토큰이 0.6초에서 8.8초로, 응답 시간 p95가 9.7초에서 19.6초로 늘어난다.
- KV 캐시는 4%도 못 쓴다. 메모리(동시 34개 가능)가 아니라 **`max_num_seqs` 설정이 병목**이다.

**표 읽을 때 주의:** 앱은 단계를 "문서가 그 단계의 일꾼에게 넘어갈 때" 바꾼다. 그래서 `전처리 구간`에는 추출 일꾼을 기다린 시간이, `추출 구간`에는 `model_gate`를 기다린 시간이 들어 있다(동시 1의 전처리 67.8초, 동시 6의 추출 75.9초가 그 때문). **대기 없이 순수한 값**은 동시 6의 전처리(≈10초)와 동시 1의 추출(≈19초), 검증(≈9~10초)에 가깝다. 문서 하나를 혼자 처리하면 전처리 ≈10초 + 추출 ≈19초 + 검증 ≈10초 ≈ 40초(첫 문서 완료 42.5초와 일치).

해석:
- **문서 동시 1 → 3으로 총 시간이 39% 줄었다.** 팀이 L40S 48GB에서 잰 값(3건 동시 225 → 169초, 25%)보다 이득이 크다.
- **6은 3보다 느리다.** 그런데 vLLM은 6일 때 더 바쁘지 않았다(실행 중 평균 4.6 < 4.9, 대기 0, KV 4%). 병목이 **vLLM이 아니라 그 앞단**으로 옮겨 갔을 가능성이 크다.
- 동시 6에서는 6건이 98~148초에 몰려 끝난다. **어느 문서도 일찍 끝나지 않는다**(첫 문서 완료 98초, 3일 때 45초).
- **`model_gate`의 효과**: 게이트 없이 vLLM에 직접 16개를 보내면(E1) 대기가 평균 6.6개였지만, 앱을 거치면 문서를 6건 동시에 올려도 vLLM 대기는 최대 0~3이었다. 대기가 vLLM 안이 아니라 앱 안으로 옮겨져 vLLM 대기열이 짧게 유지된다.

### 미검증 가설 (동시 6이 느린 이유)
1. 한 앱 프로세스에서 6개 문서를 동시에 돌려 **CPU·파이썬 GIL**이 막힘 (확인: 실험 중 `docker stats`로 app CPU 측정)
2. `model_gate`가 여러 문서의 항목 호출을 섞어 처리해 문서 단위 완료가 늦어짐
3. 요청 구성이 섞여(prefix 공유 감소) 처리 효율이 떨어짐 (확인: prefix 적중률 비교)

## 7. OCR·판정까지 포함한 전체 흐름과 부하 시험 (같은 날 이어서 측정)

전체 흐름 = OCR(PaddleOCR + Docling, GPU) → 모델 JSON 추출 → 판정 로직 → 판정 LLM 설명. 설계는 **모델만 1건씩 점유**하고 OCR·전처리·판정 규칙은 제한 없이 동시에 돈다(추출 1건씩, 설명 1건씩). vLLM `gpu-memory-utilization` 0.72로 낮춰 OCR 워커와 한 GPU를 나눠 썼다.

### 7-1. OCR 구성 (PDF 6건, 이미지 재빌드 후 Docling GPU 확인)
| 구성 | 전체 | 비고 |
|---|---|---|
| 레거시 전처리, 문서 3건 동시 | 111초 | 3장 |
| OCR 구성, 문서 3건 동시 (`ocr_w3`) | 120초 | +8%. 문서당 큐대기 14.3, 전처리 30.6, 추출 33.3, 검증 9.8초 |
| 설계 A: OCR 워커 1, 추출 1건씩 | 197.8초 | |
| 설계 B: OCR 워커 2 | 225.9초 | |
| 설계 C: OCR 워커 6, 전처리 6, 설명 1 | 198.9초 | GPU에 vLLM 약 59.5GB + OCR 워커 6개(각 2.0~2.4GB) 동시 상주 확인 |

- **OCR은 병목이 아니다.** 워커를 1에서 6으로 늘려도 같고, OCR 결과가 추출 슬롯을 16~115초 기다렸다.
- Docling이 GPU를 못 쓰던 문제(torch/paddle의 NCCL 충돌)는 `nvidia-nccl-cu13==2.30.7`을 마지막에 재설치해 고쳤고, 새로 빌드한 이미지에서 `torch.cuda.is_available()`이 True임을 확인했다.

### 7-3. 병목 분석: 문서당 모델 단계 (실험 A, 6건 합계 165초)
| 구간 | 시간 | 비중 |
|---|---|---|
| 9개 항 첫 호출(동시, 가장 느린 항 기준) | 85초 | 52% |
| 최종 재호출(검증 오류 항을 **1개씩 직렬**) | 52초 | 31% |
| 항 안 재시도 | 약 28초 | 17% |

- 재호출(최종+항 안)이 모델 단계의 약 48%. 12건 문서 전부에서 최종 재호출이 발생(평균 2.5회). 최종 재호출 구간은 요청 1개씩이라 GPU를 약 1/4만 쓴다(E1: 동시 1개 약 170 vs 8개 약 625 tok/s).
- 검증 오류 집계(체크 파일, 항별 53건 중 항 안 재시도 횟수): 11항 48, 9항 36, 3항 35, 8항 32, 12항 24. 원인 종류는 대부분 **스키마 허용 목록 불일치**(예: 독성 지표 `LCLo`, 온도 단위 `deg C`, 규제 상태 `비해당`, 법령 `INTL_US`), 11항 `item_code`가 빈 값, 12항 표 열 개수 불일치. 같은 PDF가 같은 이유로 반복되므로 모델 출력 변동이 아니라 구조적 원인이다.
- 개선 후보(**미시행, 팀 코드 수정 필요, 효과는 추정**): ① 허용 목록·빈 값 규칙 보강으로 재호출 감소 ② 최종 재호출을 동시에 보내고 채택 판단만 순서대로 처리(문서당 약 4~5초 추정) ③ OCR 워커 시작 시 모델 선로딩(첫 문서 약 20초).

### 7-4. 정정
- "모델이 finalize 동안 논다(24% 단축 가능)"는 **틀렸다.** finalize 구간에는 직렬 모델 재호출이 들어 있다.
- "B가 느린 것은 OCR과 GPU 경쟁 때문"은 **근거가 없다.** A와 B의 차이 약 40초는 항 안 재시도가 B에서 약 31초 더 나온 것이 대부분이고(같은 PDF·설정인데 모델 출력이 달라 재시도 횟수가 다름), 첫 호출 구간은 +5%뿐이었다. **1회 측정으로는 A/B 비교가 성립하지 않는다.**
- 처음 "OCR 없는 서버"라고 한 것은 기본 구성(`compose.yaml`)이 `MSDS_PREPROCESS=legacy`이기 때문이며, OCR은 `compose.ocr.yaml`을 겹쳐야 켜진다.
